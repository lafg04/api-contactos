🚀 Laboratorio Práctico - Unidad 4.5Nivel Intermedio: Forking Workflow y Pull RequestsRepositorio Oficial: api-contactos📋 Contexto y RequerimientosIntroducción: El Triángulo de ColaboraciónEn un entorno corporativo de alta seguridad o en proyectos Open Source (Código Abierto), usted no tendrá permisos de escritura en el repositorio oficial. Si tuviera acceso directo, un solo error de código podría derribar todo el sistema de la empresa.Para colaborar de forma segura, utilizaremos el Forking Workflow. Este modelo crea un "triángulo de colaboración" entre tres puntos clave:🏢 Upstream (El Repositorio Oficial): Es el proyecto central de la empresa en GitHub. Es la fuente de la verdad. Usted solo puede leer y descargar de aquí.☁️ Origin (Su Fork Personal): Es una fotocopia exacta del Upstream alojada en su cuenta personal de GitHub. Al ser su propia copia, aquí tiene permisos totales para subir experimentos.💻 Local (Su Computadora): Su área de trabajo física. Usted descargará código oficial del Upstream, escribirá nuevas funciones, y las subirá a su Origin.💡 Analogía Docente: El Periodista y el Jefe de EdiciónUsted es un periodista (Desarrollador Junior). No tiene la llave de la imprenta central (Upstream) para publicar la noticia en el periódico de mañana. Por lo tanto, escribe y corrige el artículo en su propia máquina de escribir (Origin/Fork).Cuando termina, le entrega el borrador al Jefe de Edición a través de un Pull Request. El jefe lee su trabajo y, solo si cumple los estándares, él se encarga de enviarlo a la imprenta.🛠️ Instrucciones paso a paso⚠️ IMPORTANTE: En las instrucciones de código a continuación, NO escribas el símbolo del dólar ($). Además, sustituye las URLs de los ejemplos por las rutas reales de tu navegador.Fase 1: La Bifurcación (Creando su propio patio de juegos)El primer paso antes de programar es obtener nuestra propia copia en la nube, donde podremos romper y experimentar sin miedo a dañar a la empresa.Acciones en GitHub Web:Inicie sesión en GitHub.com.Navegue hacia el repositorio público api-contactos asignado por el docente (Nuestro Upstream simulado).En la esquina superior derecha del repositorio oficial, haga clic en el botón Fork (Bifurcar).En la pantalla de confirmación, mantenga el nombre original y haga clic en Create fork.Resultado: GitHub lo redirigirá a una página idéntica, pero notará que en la esquina superior izquierda ahora dice su-usuario / api-contactos. ¡Ya tiene su propia nube!Fase 2: Clonado y Configuración de Doble EnlaceAhora que tenemos nuestro Fork en la nube, debemos descargarlo a nuestra computadora y configurar Git para que conozca las direcciones de nuestra copia y la de la empresa oficial.🚨 Acción Crítica: En la página de SU FORK, haga clic en el botón verde Code y copie la URL HTTPS. ¡Asegúrese de que la URL contenga su nombre de usuario y no el del docente!# 1. Clone SU FOTOCOPIA personal (Origin) a su computadora
$ git clone [https://github.com/su-usuario/api-contactos.git](https://github.com/su-usuario/api-contactos.git)

# 2. Ingrese a la carpeta del proyecto
$ cd api-contactos

# 3. Conecte el cable hacia el REPOSITORIO OFICIAL de la empresa (Upstream).
# Reemplace la URL por la direccion original del repositorio del docente.
$ git remote add upstream [https://github.com/docente/api-contactos.git](https://github.com/docente/api-contactos.git)

# 4. Verifique su libreta de contactos. Deberia ver 4 lineas en total.
$ git remote -v
# origin   (Apunta a su cuenta -> Lectura y Escritura)
# upstream (Apunta a la empresa -> Lectura y Escritura bloqueada)
Fase 3: Desarrollo en Aislamiento (Documentation Branches)Aplicaremos una regla inquebrantable de la industria corporativa: JAMÁS se programa directamente en la rama main.# 1. Descargue siempre las ultimas actualizaciones oficiales de la empresa 
# antes de empezar a trabajar. (Asegurese de estar en main)
$ git pull upstream main

# 2. Cree una nueva rama aislada para su tarea de documentacion (docs/)
$ git switch -c docs/mejorar-readme

# 3. Modifique este archivo README.md usando Markdown. Para este lab, ejecutaremos:
# (Nota: Esto sobrescribirá las instrucciones actuales, asegúrate de haberlas leído)
$ echo "# Directorio de Contactos" > README.md

# 4. Empaquete (Commit) su trabajo localmente
$ git add README.md
$ git commit -m "docs: estructura inicial del readme"

# 5. Envie esta nueva rama hacia SU NUBE personal (Origin)
$ git push -u origin docs/mejorar-readme
🛑 Precaución Importante: Si por error de tipeo intenta ejecutar git push upstream main, GitHub detectará que no tiene permisos de administrador en el repositorio oficial y le devolverá un Error 403: Forbidden (Prohibido). El sistema lo bloquea automáticamente para proteger a la empresa.🎯 El Reto y Entregable: La Revisión de Código (Code Review)Usted ha enviado su excelente documentación a su propio GitHub (origin). Ahora debe tocar la puerta de la empresa y pedirles que integren su trabajo mediante un Pull Request (PR).En el mundo real, los líderes rara vez aprueban un cambio a la primera; le pedirán que corrija detalles. Su reto final es responder a esta revisión dinámicamente y enviar la evidencia.Abrir el Pull Request (PR): Vaya a la página web de su Fork en GitHub. Verá un banner verde notificando su empuje reciente con el botón Compare & pull request. Haga clic ahí.Revise las flechas de fusión: Asegúrese de que apunten de la siguiente forma:base: main (Empresa) ← compare: docs/mejorar-readme (Usted).Escriba un título descriptivo y haga clic en Create pull request.La Crítica (Simulación): El Líder Técnico revisa su PR, nota deficiencias y le comenta: "El archivo está incompleto. Por favor agrégale un correo electrónico de la empresa antes de que te apruebe la integración".🧠 El Secreto Técnico de los Pull Requests: Un Pull Request en GitHub no evalúa sus commits estáticos; evalúa el estado vivo de su rama. Esto significa que si usted sube nuevos cambios a la misma rama de su Fork en la terminal, el PR en la web se actualizará mágicamente solo.La Solución Local: ¡No cierre su Pull Request en la web! Regrese a la terminal en su computadora. Verifique que sigue parado en su rama de trabajo ejecutando git status.Corrija el archivo según lo solicitado por el líder (note el uso de >> para inyectar texto sin borrar el título anterior):$ echo "**Email de Soporte:** soporte@empresa.com" >> README.md
Empaquete la corrección y envíela a su nube:$ git add README.md
$ git commit -m "fix: correo de soporte agregado al readme"

# Envie de nuevo. (Ya no necesitamos la bandera -u)
$ git push origin docs/mejorar-readme
